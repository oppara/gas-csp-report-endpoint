# CSP違反レポート受信エンドポイント 実装仕様

## 概要

CSP(Content-Security-Policy)の`report-to` / `report-uri`で送られてくる違反レポートを受信し、
許可された送信元サイトからのものだけを記録・Slack通知する、Google Apps Script(GAS)製のエンドポイントを実装する。

## 目的

- ブラウザが自動送信するCSP違反レポートを受け取る
- **想定していないサイト(第三者による偽装リクエスト等)からのレポートは拒否する**
  (GASのウェブアプリURLは公開されるため、URLを知っていれば誰でもPOSTできてしまうことへの対策)
- 許可されたサイトからの違反レポートはログとして記録し、Slackに通知する
- **許可されていないサイトからのリクエストがあった場合も、Slackに通知する**(不正利用の早期検知が目的)
- ドメイン単位でのリクエスト状況(初回・最新の検知日時)を別シートで一覧できるようにする

## 実行環境

- Google Apps Script(スプレッドシートにコンテナバインドする形式)
- デプロイ形式:ウェブアプリ(Web App)

## スプレッドシート構成

同一のスプレッドシート内に、以下3つのシートを用意する。

### シート1: `allowed_source_sites`

CSP違反レポートの送信元として許可するサイト(`document-uri`のホスト名)を管理する。

| 列名 | 型 | 説明 |
|---|---|---|
| ホスト名 | 文字列 | 許可するホスト名(例: `example.com`)。完全一致で判定するため、サブドメインごとに行を分ける(`www.example.com`と`example.com`は別行) |
| memo | 文字列 | 用途メモ(任意、処理では使用しない) |

- 1行目はヘッダー行。
- データは2行目以降。
- 空のホスト名行は判定処理で除外する。

### シート2: `violation_log`

受信した違反レポートを記録する。許可サイトからの「受理」レポートのみ記録し、未許可サイトからの「拒否」レポートは記録しない。

| 列名 | 型 | 説明 |
|---|---|---|
| 受信日時 | 日時 | レポート受信時のタイムスタンプ |
| document-uri | 文字列 | 違反が発生したページのURL(レポート内の`document-uri`) |
| blocked-uri | 文字列 | ブロックされたリソースのURI(レポート内の`blocked-uri`) |
| violated-directive | 文字列 | 違反したディレクティブ(レポート内の`violated-directive`) |

- 1行目はヘッダー行。
- 新しい行は末尾に追記(`appendRow`)。
- 許可サイトからのリクエストのみ記録する(未許可サイトからのリクエストは記録しない)。

### シート3: `request_log`

`document-uri`のホスト名(ドメイン)単位で、リクエストの初回検知日時と最新検知日時を記録する。
1リクエストごとに行を追加するのではなく、**同一ドメインであれば既存行を更新する(upsert)**。

| 列名 | 型 | 説明 |
|---|---|---|
| ホスト名 | 文字列 | `document-uri`のホスト名(レポートを送ってきたページのドメイン) |
| 初回アクセス日時 | 日時 | このドメインからのリクエストを最初に検知した日時 |
| 最終アクセス日時 | 日時 | このドメインからの直近のリクエストを検知した日時 |
| 種別 | 文字列 | 直近のリクエストの判定結果(`受理` または `拒否(未許可サイト)`) |

- 1行目はヘッダー行。
- `ホスト名`列を検索キーとして、既存行があれば`最終アクセス日時`と`種別`を更新し、なければ新規行を追加(`初回アクセス日時` = `最終アクセス日時` = 現在時刻)する。
- `種別`は同一ドメインでも直近の判定結果で毎回上書きする(過去に許可されていたドメインが後から`allowed_source_sites`から外れた場合等、最新の状態を反映する)。
- 許可・未許可を問わず、受信した全リクエストのドメインを記録する。

## 処理フロー(`doPost`関数)

1. リクエストボディ(`e.postData.contents`)をJSONとしてパースする。
2. レポート本体を取得する。以下2種類の送信形式に対応する。
   - `report-uri`形式: `{"csp-report": {...}}` (キーが存在しない場合は空オブジェクトとして扱う)。1件のレポートとして扱う。
   - `report-to`形式(Reporting API): `[{"type": "csp-violation", "body": {...}}, ...]` の配列。
     `type`が`csp-violation`の要素のみを対象とし、それぞれを独立したレポートとして扱う
     (1回のPOSTに複数件のレポートがバッチで含まれる場合、全件処理する。該当要素が無い場合は空オブジェクト1件として扱う)。
   - いずれの形式も、以下のキー名に正規化してから3以降の処理に渡す。
     - `report-uri`形式: `document-uri` / `blocked-uri` / `violated-directive`
     - `report-to`形式: `body.documentURL` / `body.blockedURL` / `body.effectiveDirective` を、上記と同じキー名に読み替える
3. 正規化されたレポート(複数件の場合は1件ずつ)から以下の値を取り出す。
   - `document-uri`
   - `blocked-uri`
   - `violated-directive`
4. `allowed_source_sites`シートのデータを全行取得し、ヘッダー行を除いた`ホスト名`列の値一覧を作る(空値は除外)。この一覧は1リクエスト内の全レポートで共通して使う。
5. `document-uri`をURLパースし、ホスト名(`hostname`)を取り出す。
   - パースに失敗した場合(不正な形式のURI等)は「許可サイトではない」と判定する。
6. 取り出したホスト名が、許可ドメイン一覧のいずれかと**完全一致**するか判定する。
   - 部分一致・`includes`判定は使用しない(`evil-example.com`等の偽装ドメインを誤許可するリスクがあるため)。
7. `request_log`シートに対して、取り出したホスト名で**upsert**を行う(許可・未許可を問わず実施)。
   - 既存行(`ホスト名`が一致する行)があれば、その行の`最終アクセス日時`を現在時刻で、`種別`を今回の判定結果で更新する。
   - 既存行がなければ、新規行を追加し`初回アクセス日時`と`最終アクセス日時`をともに現在時刻、`種別`を今回の判定結果とする。
8. 判定結果に応じて分岐する。

   **許可サイトではない場合:**
   - `violation_log`には記録しない。
   - Slackにwebhook経由で通知する(**リクエストが来るたび毎回**通知する。通知内容は下記「未許可サイトからのリクエストの通知」を参照)。

   **許可サイトの場合:**
   - `violation_log`に「受理」として1行追記する。
   - Slackにwebhook経由で通知する(通知内容は下記「許可サイトからの違反レポートの通知」を参照)。

9. 手順3〜8を、含まれる全レポートについて繰り返す。
10. レスポンスを返す。1リクエスト内のレポートが1件でも「許可サイトではない」と判定されていれば
    `{"status": "rejected"}`、全件が許可サイトからであれば`{"status": "ok"}` をJSONで返す。

## Slack通知の内容

Slack通知は2種類あり、それぞれ通知文言を分けて、どちらの通知か一目で判別できるようにする。

### 許可サイトからの違反レポートの通知

許可サイトからの違反レポートを受理した場合に通知する。

```
⚠️ CSP違反レポート受信
サイト: {document-uri}
ディレクティブ: {violated-directive}
ブロックされたURI: {blocked-uri}
```

### 未許可サイトからのリクエストの通知

`allowed_source_sites`に登録されていないドメインからリクエストがあった場合、**毎回**通知する。

```
⛔ 未許可サイトからのCSPレポート受信
サイト: {document-uri}
ディレクティブ: {violated-directive}
ブロックされたURI: {blocked-uri}
```

- Webhook URLはコード内に直接記述せず、Apps Scriptの「スクリプト プロパティ」(`PropertiesService.getScriptProperties()`)に格納し、コードからはプロパティ経由で読み込むこと。
  (仕様書には含めていないが、実装時にハードコーディングを避けるための注意点として明記)

## レスポンス仕様

いずれの場合も、Content-Typeは`application/json`とし、HTTPステータスは200を返す(CSPレポート送信側のブラウザはレスポンス内容を評価しないが、拒否時も200を返すことで、送信元にエラーとして扱われる/リトライされることを避ける)。

| 判定結果 | レスポンスボディ |
|---|---|
| 受理 | `{"status": "ok"}` |
| 拒否 | `{"status": "rejected"}` |

## エラーハンドリング

- リクエストボディがJSONとしてパースできない場合、または想定するキー構造(`csp-report`)が存在しない場合も、処理を停止させず、空文字列や空オブジェクトとして扱って拒否判定・Slack通知まで到達させること(この場合`violation_log`には記録しない)。
- `allowed_source_sites`シートまたは`violation_log`シートが見つからない場合はエラーとする(実装時に例外処理を入れるか、事前のシート存在チェックを入れる)。

## デプロイ設定

- 「デプロイ」→「新しいデプロイ」→ 種類「ウェブアプリ」を選択
- 「次のユーザーとして実行」:自分
- 「アクセスできるユーザー」:全員
- デプロイ後に発行されるURL(`https://script.google.com/macros/s/xxxxx/exec`)を、CSPの`report-to`(および`report-uri`)のエンドポイントとして設定する

## 非対象(今回のスコープ外)

- CSPリソース許可ドメイン(`connect-src`, `script-src`等で許可する外部ドメイン)の管理は本仕様の対象外とする。
- 「既知の違反」と「未知の違反」を分類してSlack通知のノイズを減らす機能は、今回は実装しない(将来的な拡張候補として検討の余地あり)。
