CSP report-uri / report-to 検証ページ

report-uri・report-toともに<meta>タグ経由のCSPでは 仕様上無視される。このHTMLを配信するサーバー側でレスポンスヘッダーを付けること。

ヘッダー設定(report-uri + report-to を併用)

report-toは2026年にBaseline入りし、Chrome/Edge/Firefox/Safariの最新版で対応済み。 ただし旧バージョンのブラウザ向けフォールバックとしてreport-uriも併記するのが定石。 両方指定した場合、report-toに対応しているブラウザはそちらを優先して使う。 

Content-Security-Policy: default-src 'self'; script-src 'self'; report-uri https://script.google.com/macros/s/xxxxx/exec; report-to csp-endpoint
Reporting-Endpoints: csp-endpoint="https://script.google.com/macros/s/xxxxx/exec"

report-to(Reporting API)対応ブラウザは Content-Type: application/reports+jsonで [{"type": "csp-violation", "body": {"documentURL": ..., "blockedURL": ..., "effectiveDirective": ...}, ...}] という配列形式・別フィールド名でレポートを送る(1回のPOSTに複数件バッチされる場合がある)。 report-uriの{"csp-report": {...}}形式とはペイロード構造が異なるが、 GAS側(parseRequestBody)は両方の形式に対応済みで、 report-toバッチ内の各レポートもそれぞれ独立した違反として記録・通知する。

https://script.google.com/macros/s/xxxxx/execは実際のデプロイURLに差し替える。

違反トリガー

下のインラインスクリプトと外部画像はCSPでブロックされる想定。 ブロックされれば違反レポートが上記URLに送信される。

確認方法

  1. ブラウザの開発者ツール(Network/Console)で、上記エンドポイントへのPOSTが発生することを確認する。
  2. GASのスプレッドシートでviolation_log(許可ドメインの場合)または request_logへの記録とSlack通知を確認する。
